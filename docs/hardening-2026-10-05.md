## Исправлено

- Возврат ограничен фактически оплаченным остатком. Частичный возврат больше не
  помечает весь платёж возвращённым. Денежные вычисления используют Decimal.
- Подтверждение, возврат и выпуск средств сериализованы блокировкой платежа.
  Повторное подтверждение не создаёт второй CAPTURE, повторный выпуск — второй RELEASE.
- Принятие котировки блокирует RFQ и котировку; уникальный индекс запрещает два заказа
  для одной котировки. Заказ, позиции и график оплаты создаются в одной транзакции.
- Заблокированные/удалённые компании исключены из доступного контекста пользователя
  и доступа партнёрского API. Загрузка файлов проверяет разрешения для своей области.
- Смена пароля отзывает прежние сессии и ссылки сброса. Сброс пароля атомарно
  погашает токен и отзывает сессии. Добавлены лимиты входа по IP и учётной записи.
- HTML из Markdown проходит allowlist-парсер вместо регулярных выражений.
- Лимиты запросов используют общий Redis при наличии REDIS_URL и закрывают доступ
  при его недоступности. Исправлена гонка счётчика в локальном fallback.
- Seed сохраняет администраторские тарифы, комиссии, настройки и состояние провайдеров;
  обычный деплой больше не запускает seed. Новый production-admin требует явного пароля.
- Новые уведомления о создании/статусах заказов и подтверждении/выпуске платежей
  учитывают вьетнамскую локаль получателя. Старые уведомления не переписываются.
- Health endpoint не раскрывает текст ошибок БД. Обновлён PostCSS, закреплены pnpm
  и Node 22, добавлены ESLint и обязательный CI перед автоматическим деплоем.
- Деплой делает резервную копию до изменений. При неудаче возвращает предыдущие
  исходники, Compose, Caddy и фактический образ, затем проверяет версию и здоровье.
- Первичная установка прекращает работу при ошибке, не включает shell-трассировку
  секретов и демо-данные, не перезаписывает существующую установку.
- Резервные копии получают закрытые права, уникальные имена, проверку архива,
  атомарную публикацию и checksum. Добавлена проверка восстановления в отдельную БД.

## Что требует доступа владельца

Порядок первого выпуска описан в [deploy/README.md](../deploy/README.md).
Старый timer надо остановить до первого push и предварительно обновить deploy-скрипты:
иначе он не будет ждать новый CI и не получит новую защиту первого обновления.

1. Проверить исторические дубли заказов до миграции 0004; миграция не удаляет данные.
2. Проверить восстановление VPS-backup и настроить копирование вне VPS.
3. Отозвать ранее раскрытый GitHub token, выдать read-token с Contents/Actions,
   затем сделать репозиторий приватным.
4. Сменить существующие демонстрационные пароли и проверить демо-данные. Старый
   bootstrap включал `set -x`: проверить доступ к его журналу и заменить секреты,
   которые могли быть записаны туда (DB password, SESSION_SECRET, admin password).
5. Подключить email-провайдера, проверить DNS отправителя и доставку реальных писем.
6. Подтвердить банковские реквизиты и правила ручного учёта. Текущий адаптер не
   переводит реальные деньги; подключение платёжного шлюза — отдельная интеграция.
7. Проверить и продлить домен в iNET: заявленная владельцем дата — 20 октября 2026.

Доступ по имеющимся SSH-ключам к VPS не прошёл. Секреты, production-база и настройки
аккаунтов провайдеров не менялись. Автоматический откат схемы БД не выполняется;
миграции автоматических выпусков должны быть совместимы с предыдущим кодом.
